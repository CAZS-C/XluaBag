# 背包系统架构方案（简历级）

## 项目定位

> **Unity ARPG 客户端框架 Demo** — 以背包系统为切入点，展示模块化架构、性能优化、热更新管线和事件驱动设计能力。

这不是一个"实现了背包功能"的项目，而是一个**以背包为载体的客户端架构演示**。

---

## 一句话概括

> **C# 做稳定框架和数据层，Lua 做易变业务逻辑，事件系统解耦模块通信，对象池+虚拟滚动保证性能，AB 管线支撑热更新。**

# 一、整体架构

## 分层设计

```
┌──────────────────────────────────────┐
│         UI 渲染层 (Unity uGUI)        │  ← 只负责显示，不存状态
├──────────────────────────────────────┤
│         Lua 业务逻辑层                 │  ← 高频修改：Tab切换、筛选、交互
├──────────────────────────────────────┤
│         C# 核心框架层                  │  ← 低频修改：数据管理、事件、资源加载
├──────────────────────────────────────┤
│         Unity 底层引擎                │  ← 渲染、输入、资源
└──────────────────────────────────────┘
```

**核心原则：上层依赖下层，下层不知道上层存在。** 数据层不引用 UI 命名空间，UI 层通过事件被动响应数据变化。

## 为什么用 Lua？

| 问题 | 纯 C# 方案 | C# + Lua 方案 |
|------|-----------|---------------|
| 改背包排序规则 | 改 C# → 编译 → 重启 → 发包 | 改 Lua → 秒级生效 |
| 加一个"一键整理"按钮 | 同上 | 改 Lua，热更新 |
| AB 包体更新 | 全量 | Lua 文本，极小 |

**C# 做稳定系统（框架、数据、性能），Lua 做善变业务（交互、排序、筛选）。**

# 三、核心模块设计

## 1. 数据定义 — 唯一数据源

**旧方案的问题：** C# `ItemData` 和 Lua `ItemConfig` 各存了一份 name/type/quality/icon，数据流不清晰。

**新方案：**

```
Lua ItemConfig.lua（唯一数据源，策划直接改）
       │
       ▼
C# ConfigManager（启动时加载进内存）
       │
       ▼
C# ItemDefinition（只读运行时对象）
```

**ItemConfig.lua** — 策划维护，热更新可替换：

```lua
ItemConfig = {
    [1001] = { name="铁剑", type="Equipment", quality=2, icon="icon_sword_01", stackMax=1 },
    [2001] = { name="生命药水", type="Consumable", quality=1, icon="icon_potion_01", stackMax=99 },
    [3001] = { name="红宝石", type="Gem", quality=3, icon="icon_gem_atk_01", stackMax=10 },
}
```

**ItemDefinition.cs** — C# 运行时只读对象，通过 ConfigManager 从 Lua 加载后不可修改：

```csharp
// 静态模板（只有一个副本，被多个 ItemInstance 引用）
public class ItemDefinition
{
    public int id;
    public string name;
    public ItemType type;
    public QualityLevel quality;
    public string iconPath;     // AB 内的图标路径
    public int stackMax;        // 最大堆叠数

    // 从 Lua 配置创建
    public static ItemDefinition FromLuaTable(LuaTable data);
}
```

**为什么消除重复？** name/type/quality/icon 只定义一次（在 Lua 里）。C# 通过加载拿到只读副本，不会再有两边不同步的问题。

---

## 2. ItemDefinition / ItemInstance 分离

**旧方案的问题：** `ItemData` 里同时混了静态属性（id/name）和运行时属性（count），装备类的强化/宝石没地方放。

**新方案：** 拆成静态模板 + 运行时实例 + 格位。

### 静态模板（物品"是什么"）

```csharp
public class ItemDefinition
{
    public int id;
    public string name;
    public Sprite icon;
    public ItemType type;
    public QualityLevel quality;
    public int stackMax;
}
```

所有同 ID 物品共享同一个 Definition 引用，不重复存储。

### 运行时实例（物品"这个个体"）

```csharp
public class ItemInstance
{
    public int uid;                  // 实例唯一 ID（全局自增）
    public ItemDefinition definition;// 指向模板，只读
    public int level;                // 强化等级（装备类使用）
    public List<int> gemIds;         // 镶嵌宝石（装备类使用）
}
```

消耗品（药水）大概率没有 uid/level/gems，但统一留空不额外占用。**数据结构预留了装备扩展，但不实现装备系统本身。**

### 格位（背包的一个槽）

```csharp
public class ItemSlot
{
    public ItemInstance instance;    // 指向运行时实例（可 null）
    public int count;                // 当前数量（堆叠时 >1，装备类 =1）

    public bool IsEmpty => instance == null || count == 0;
}
```

**三层结构的关系：**

```
ItemConfig[1001]──→ItemDefinition{id=1001,name="铁剑",...}
                           ↑
                    ItemInstance{uid=500001, definition→↑, level=5}
                           ↑
                    ItemSlot{instance→↑, count=1}
```

**面试话术：** "我把数据结构拆成了三层——Definition 是静态模板，全局共用；Instance 是运行时个体，uid 唯一，装备的强化/宝石状态存在这里；Slot 是背包格位，一个格位可以放多个堆叠的同类物品。这样无论是展示背包、做装备系统还是存档，数据结构都只需要增补细节，不需要重构。"

## 3. EventSystem — 事件总线

**为什么需要？** 直接的模块调用是"硬依赖"：InventoryManager 改了数据后要调 `BagPanelCtrl.Refresh()`，这就导致数据层知道了 UI 层的存在，违反了分层原则。事件总线让数据层只负责"发事件"，谁订阅谁处理。

```csharp
// 事件定义
public class InventoryEvent
{
    // 格子数据变化（新增、移除、数量变化）
    public event Action<SlotChangeData> OnSlotChanged;

    // 选中变化
    public event Action<int, int> OnSelectionChanged;  // prevIndex, newIndex
}

public struct SlotChangeData
{
    public int index;           // 格子索引
    public ItemInstance item;   // 物品实例（null = 格子清空）
    public int count;           // 当前数量（0 = 移除）
}
```

**事件粒度控制：** SlotChangeData 包含了 UI 刷新所需的全部信息（哪个格子变了、变了什么），UI 收到事件后只刷那个格子，不用全量刷新。这是比 `OnInventoryChanged()` 朴素事件更工程化的设计。

## 4. InventoryManager — 数据层核心

**关键约束：不引用任何 UI 命名空间，不知道 BagPanel 的存在。**

```csharp
public class InventoryManager : SingletonMono<InventoryManager>
{
    private List<ItemSlot> slots = new List<ItemSlot>();
    private int maxSlots = 99;

    // ── 数据操作（只改数据，不管 UI）──
    public bool AddItem(int defId, int count = 1);
    public bool RemoveItem(int slotIndex, int count = 1);
    public bool MoveItem(int fromIndex, int toIndex);
    public void Sort(ItemSortRule rule);     // Lua 传入排序规则
    public List<ItemSlot> GetFilteredSlots(ItemType type);

    // ── 事件（数据层改完就发，谁订阅谁处理）──
    public event Action<SlotChangeData> OnSlotChanged;
    public event Action<int, int> OnSelectionChanged;

    // ── 存档（序列化/反序列化）──
    public string Serialize();                // slots → JSON
    public void Deserialize(string json);    // JSON → slots

    // AddItem 内部：
    //   1. 查找同 ID 可堆叠空位（可堆叠 && count < stackMax）
    //   2. 找不到 → 找空 Slot → 创建 ItemInstance
    //   3. 修改数据
    //   4. OnSlotChanged?.Invoke(...) — 不调任何 UI 方法
}
```

**InventoryManager.AddItem 的参数是 `int defId` 不是 `ItemDefinition`。** 它在内部通过 ConfigManager 获取 Definition，自己创建 ItemInstance。Lua 层只需要传一个配置表 ID，不需要关心 C# 对象构造。

**为什么数据层用 C# 不用 Lua？**

- 物品增删改查是高频操作，C# 性能更好
- ItemSlot 是 C# 对象，Lua 频繁访问有跨语言开销
- 防止 Lua 和 C# 各存一份数据，导致数据不一致
- 存档序列化在 C# 层做，Lua 只负责业务规则

## 5. C# 和 Lua 的职责边界（精确版）

**这是旧方案没有明确讲清楚的地方。旧方案只说"C# 做稳定、Lua 做易变"，但没落到代码级别。**

正式约定：

| 职责 | 归 C# | 归 Lua | 原因 |
|------|-------|--------|------|
| 物品增删改查 | ✅ | | 高频操作、数据一致 |
| 虚拟滚动计算 | ✅ | | 每帧触发，跨语言调用有 GC |
| 对象池管理 | ✅ | | GameObject 生命周期管理 |
| AB 加载/卸载 | ✅ | | 底层资源操作 |
| 存档序列化 | ✅ | | 数据完整性和格式 |
| 事件总线 | ✅ | | 模块解耦基础设施 |
| **Tab 切换逻辑** | | ✅ | 频繁修改 |
| **排序规则** | | ✅ | 方便热更新 |
| **筛选规则** | | ✅ | 方便热更新 |
| **格子的图标/数量绑定** | | ✅ | 业务逻辑 |
| **点击/长按/拖拽响应** | | ✅ | 交互逻辑 |

**精确到方法级别的约定：**

- `BagGridLayout.OnScroll()` → C#（每帧触发的性能路径）
- `BagGridLayout.Refresh(count)` → C#（Content 高度计算）
- `BagItemPool.Get(index)` → C#（GameObject 管理）
- `BagItemPool.OnCellBind(index, cellGo)` → **回调到 Lua**（图标、数量、品质色）
- `BagPanelCtrl.OnTabChanged(type)` → Lua（筛选 + Refresh 调用）
- `ItemCellCtrl.OnClick(slotIndex)` → Lua（选中/使用）

## 6. BagGridLayout + BagItemPool — 虚拟滚动

**核心问题：500 个物品，如果每个建一个 GameObject = 500 个格子。每个格子的 RectTransform + Image + Button + Text 加起来在 Canvas 重建时开销巨大。**

**解决方案：只生成可见区域的格子（约 20 个），滑动时复用。**

```
┌──────────────────────────────┐
│  可见区域（Viewport）          │
│  ┌────┐ ┌────┐ ┌────┐ ┌────┐│
│  │格0 │ │格1 │ │格2 │ │格3 ││  ← 只有这 12~20 个 GameObject
│  └────┘ └────┘ └────┘ └────┘│
│  ┌────┐ ┌────┐ ┌────┐ ┌────┐│     总数据 500 条
│  │格4 │ │格5 │ │格6 │ │格7 ││     Content 高度拉满
│  └────┘ └────┘ └────┘ └────┘│     但实体的格子只有 20 个
│  ┌────┐ ┌────┐ ┌────┐ ┌────┐│
│  │格8 │ │格9 │ │格10│ │格11││
│  └────┘ └────┘ └────┘ └────┘│
├─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┤
│  下滑 → 格格格格移到最下面     │
│  数据换绑，GameObject 不销毁   │
└──────────────────────────────┘
```

**BagGridLayout.cs** — 挂在 Content 节点上：

| 配置参数 | 值 | 说明 |
|----------|-----|------|
| colCount | 4 | 一行 4 个 |
| cellSize | (176, 176) | 格子大小 |
| spacing | 8 | 格子间距 |
| padding | 12 | 内边距 |

```csharp
// 核心计算
总行数 = ceil(itemCount / colCount)
Content高度 = 总行数 × (cellSize.y + spacing.y) + padding.top + padding.bottom

格子(i) 坐标:
  col = i % colCount
  row = i / colCount
  x = padding.left + col × (cellSize.x + spacing.x) + cellSize.x/2
  y = -(padding.top + row × (cellSize.y + spacing.y) + cellSize.y/2)

可见行范围:
  firstVisibleRow = floor(Content.offset.y / (cellSize.y + spacing.y))
  lastVisibleRow = ceil((viewport.height + cellSize.y) / (cellSize.y + spacing.y)) + firstVisibleRow
```

**BagItemPool.cs** — 预实例化，按需分配：

| 参数 | 值 |
|------|-----|
| 池容量 | colCount × (可见行数 + 2 缓冲行) = 4 × (5+2) = **21 个** |
| 预实例化 | Awake 时 Instantiate 21 个 BagItemCell |
| Get(index) | 取空闲格子 → 计算位置 → 回调 Lua OnCellBind |
| RecycleAll() | 全部回收（Tab 切换时） |

## 7. 存档系统（极轻量）

不引入第三方库，不做云存档，**只用 JSON 实现本地存档**，体现"数据驱动"和"数据完整性"思维。

```csharp
public class PlayerData : SingletonMono<PlayerData>
{
    public int gold;
    public List<ItemSlot> inventorySlots = new List<ItemSlot>();

    public void Save()
    {
        string json = JsonUtility.ToJson(this);
        PlayerPrefs.SetString("PlayerData", json);
        PlayerPrefs.Save();
    }

    public void Load()
    {
        string json = PlayerPrefs.GetString("PlayerData", "");
        if (!string.IsNullOrEmpty(json))
            JsonUtility.FromJsonOverwrite(json, this);
    }
}
```

**为什么这是加分项？** 大多数学生项目忽略了这个环节。面试官可以沿着"获取物品 → 存入背包 → 保存 → 重启 → 加载 → 物品还在"这条闭环问下去，存档系统提供了闭环的最后一环。

# 四、完整调用流程

## 流程一：打开背包，切换 Tab

```
用户点击 Equip Tab
  │
  ▼
Lua: BagPanelCtrl.OnTabChanged("Equip")
  │ ① 调 InventoryManager.GetFilteredSlots(ItemType.Equipment)
  │ ② 拿到筛选后的 List<ItemSlot>
  │ ③ 调 bagGridLayout.Refresh(slotCount)
  │
  ▼
C#: BagGridLayout.Refresh(int count)
  │ ① 算 Content 总高度
  │ ② 设 Content.sizeDelta
  │ ③ 监听 ScrollRect.onValueChanged
  │
  ▼ 滚动每帧触发
C#: BagGridLayout.OnScroll(normalizedPos)
  │ ① 算 firstVisibleRow / lastVisibleRow
  │ ② BagItemPool.Get(index) → 移格子到正确位置
  │ ③ BagItemPool.Recycle(滑出可见范围的格子)
  │
  ▼ 每次 Get 出新格子
C#: BagItemPool 回调 → Lua: BagPanelCtrl.OnCellBind(index, cellGo)
  │ ① slot = filteredSlots[index]
  │ ② 设 cellGo.imgIcon.sprite = ConfigManager.GetIcon(slot.instance.definition.iconPath)
  │ ③ 设 cellGo.txtCount.text = slot.count > 1 ? slot.count : ""
  │ ④ 设 cellGo.imgQuality.color = 根据品质颜色表
```

## 流程二：使用物品（数据 + 事件）

```
用户右键"生命药水"
  │
  ▼
Lua: ItemCellCtrl.OnClick(slotIndex)
  │ ① BagPanelCtrl.SelectItem(slotIndex)
  │ ② InventoryManager.RemoveItem(slotIndex, 1)
  │
  ▼
C#: InventoryManager.RemoveItem()
  │ ① slots[index].count--
  │ ② if count == 0: 清空格子
  │ ③ 发事件：OnSlotChanged?.Invoke(data)  — 不调任何 UI
  │
  ▼
Lua: BagPanelCtrl (订阅了 OnSlotChanged)
  │ ① 收到事件 → 只刷 slotIndex 这一个格子
  │ ② count==0 → 格子设空白状态，图标隐藏
```

**关键：RemoveItem 内部没有调任何 UI 方法。** UI 更新是 Lua 订阅事件后自己做的。数据层和 UI 层完全解耦。

## 流程三：闭环 — 获取到存档

```
游戏内获得物品（NPC 赠送/商店购买）
  │
  ▼
Lua: BagPanelCtrl.AddItemToBag(2001, 5)
  │ ① InventoryManager.AddItem(defId=2001, count=5)
  │
  ▼
C#: InventoryManager.AddItem()
  │ ① 找到已有堆叠位 / 空 Slot
  │ ② 创建 ItemInstance{uid=500002, definition=ItemConfig[2001]}
  │ ③ 修改数据
  │ ④ 发 OnSlotChanged 事件
  │ ⑤ PlayerData.Save() — 存档
  │
  ▼
  下次启动游戏
  │ ① PlayerData.Load() — 读档
  │ ② Lua 打开背包 → 物品还在
```

# 六、为什么"GridLayoutGroup + 对象池"不够

| | GridLayoutGroup | BagGridLayout（本项目） |
|------|----------------|------------------------|
| 500 物品需要的 GameObject | 500 个 | ~21 个 |
| Canvas 重建开销 | O(n) 随物品数增长 | O(1) 固定 |
| 对象池兼容 | 不兼容 | 原生池支持 |
| Content 高度控制 | 自动，容器驱动 | 手动，代码精确控制 |
| 内存占用 | 每个格子 ~4 组件 = 2000+ | 每个格子 4 组件 × 21 = ~84 |

**这是简历里可以展开讲的技术决策。** 面试官问"为什么不用 GridLayoutGroup"时，答案不止"性能好"，而是"我用 O(1) 的 Canvas 重建开销替代了 O(n)"。

# 九、面试话术准备

**面试官："介绍一下你的背包系统项目。"**

> "这是一个以背包为载体的**客户端架构 Demo**。我采用了 **C# + Lua 混合架构**：C# 负责稳定的框架层——数据管理、事件总线、AB 加载、虚拟滚动渲染；Lua 负责易变的业务逻辑——Tab 切换、排序规则、筛选逻辑。

> 数据结构我拆成了 **Definition（静态模板）、Instance（运行时实例）、Slot（格位）** 三层。Definition 是只读共享的，Instance 有唯一 uid 承载装备的强化/宝石状态，Slot 负责堆叠管理。数据层通过**事件系统**和 UI 层解耦——InventoryManager 改了数据后发事件，不调任何 UI 方法，谁订阅谁处理。

> 性能方面，我用**自定义的 BagGridLayout 替代了 GridLayoutGroup**，配合**对象池**实现了虚拟滚动——500 个物品只需要约 20 个 GameObject，Canvas 重建开销是 O(1)。资源管理走 **AB 加载管线**，所有 Prefab 和图标从 AssetBundle 动态加载。

> 最后，通过 **JSON 存档**形成完整闭环：获取物品 → 存入背包 → UI 刷新 → 保存 → 重启 → 加载 → 物品还在。"

**面试官追问："为什么要拆 Definition/Instance/Slot 三层？"**

> "一开始我也只设计了一层 ItemData，但遇到两个问题：一是 47 瓶药水需要 47 个对象副本，浪费内存；二是装备有强化和宝石状态，消耗品没有，但共用同一个类。拆完后，Definition 全局共享节约内存，Instance 用 uid 唯一标识每个物品个体，Slot 负责堆叠和格位概念。**后面扩展装备只需要在 Instance 上加字段，不影响背包的其他逻辑。**"

**面试官追问："为什么事件参数是 SlotChangeData 而不是简单的 OnInventoryChanged？"**

> "OnInventoryChanged 收到后 UI 只能全量刷新所有格子。使用 SlotChangeData，我精确告诉 UI 第几格变了、变成了什么。UI 只刷那一个格子，O(1) 更新。这在 500 格的大背包里是明显的优化。"

# 十、扩展可能 — 不升层，只复用

这套框架不靠加层来扩展，而是现有模块直接复用：

| 系统 | 复用什么 |
|------|---------|
| **装备系统** | `ItemInstance.level` + `ItemInstance.gemIds` 已有，只需写 `EquipmentManager` |
| **技能面板** | `BagGridLayout` 虚拟滚动 + `BagItemPool` 对象池 |
| **任务列表** | 同上 |
| **商城** | `ABManager` + `UIManager` + 事件系统 |
| **Buff 系统** | `EventSystem` + Lua 业务逻辑 |

**这就是"架构"和"功能"的区别：功能做完就完了，架构做好了一套能复用。**
